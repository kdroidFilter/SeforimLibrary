# Lucene on a JVM, on every platform

Lucene needs a JVM, and keeps up with the newest Java (21 for Lucene 10, 25 for Lucene 11): ART can't, so the search
runs Lucene on a real JVM everywhere, and everything else (query building, dictionary, ranking, snippets, highlights,
fusion, the semantic model) in common Kotlin. The bridge between both is
[Nucleus JVM Access](https://github.com/NucleusFramework/NucleusJvmAccess) (NJA).

```
search (Kotlin Multiplatform)                         search-facade (Kotlin/JVM): what runs on the JVM
──────────────────────────────                        ─────────────────────────────────────────────────
LexicalSearchEngine, MagicDictionaryIndex, snippets,
highlights... use the façade's API as if it were      LuceneIndex(indexDir, cacheQueries): analyze, search,
local: io.github...search.index.LuceneIndex,     ──▶  cursors, facets, collectLongs, count, KNN
IndexQuery, IndexPage, KnnRequest... (generated by    IndexQuery (a sealed value), IndexPage, KnnRequest...
NJA from the façade's sources)                        LuceneIndexBackend (internal): Lucene 10
```

| | Desktop (JVM) | Android 10+ | iOS |
|---|---|---|---|
| The JVM | the app's own | HotSpot (server VM, JIT), in the app's process next to ART | Zero (interpreter: iOS forbids generated code), linked into the app |
| A call | a plain call into NJA's dispatcher, on the calling thread | handed to a HotSpot thread paired with the calling one | JNI, on the calling thread |

- `search-facade` holds the façade: its public API (`LuceneIndex`, `IndexCursor` and the value types: data classes,
  enums, the sealed `IndexQuery`) is what NJA exports; `LuceneIndexBackend` is internal.
- NJA generates, from the façade's sources, the proxies and value types `search`'s common code uses, in
  `io.github.kdroidfilter.seforimlibrary.search.index` (`njaFacade.clientPackage`: apart from the façade's own package,
  as the desktop has both on its class path). Query helpers built in the app (`bool { }`) stay in common code.
- `LuceneIndex(path)` is the same constructor on every platform; `close()` closes the JVM's index.

## The runtimes

The mobile JVMs are jdk-mobile's: a stable OpenJDK (27, `openjdk/jdk27u`'s GA releases) with openjdk/mobile's port,
built by the CI of [NucleusFramework/openjdk-mobile](https://github.com/NucleusFramework/openjdk-mobile) and published
as releases named like the JBR's, `jdk-mobile-<version>b<build>.<revision>` (`jdk-mobile-27b35.3`: `jdk-27-ga`, the
JDK's build 35). NJA downloads the latest one (the runtimes `search` needs: arm64-v8a and x86_64 Android, iOS),
checks them against their `.sha256`, keeps them in Gradle's cache and extracts them into `search/build/nja/jdkMobile`;
`nucleusJvm.jdkMobileRelease` pins one.

- **Android**: NJA links HotSpot and the JDK's natives into `libnja.so` (one per ABI: arm64-v8a, x86_64) and puts the
  runtime (`java.home` per ABI, the façade's class path, the VM's options) in `search`'s assets, extracted once per
  version on the device: an app depending on `search` gets both through the library, with nothing to configure.
- **iOS**: the binaries link jdk-mobile's static libraries (`-force_load`: the runtime finds its natives by name,
  `-export_dynamic`) and carry NJA's bundle next to the executable: `lib/` (the VM's `java.home`, which it sets to
  `<executable dir>/lib`) and `nja/` (the class path and the VM's options). For `search`'s own tests NJA does both; an
  app does them as Zayit's `searchkit` shows (`assembleIosJavaRuntimeDevice`: `static/` to link, `bundle/` to copy into
  `App.app`). About 50 MB uncompressed.
- **The desktop**: the façade is on the app's class path; nothing else.
- The VM's options are `nucleusJvm.jvmOptions` (a 128 MB heap: about 140 MB of memory on Android, 160 MB on iOS, on
  real data).

## Tests

```bash
./gradlew :search:jvmTest -PindexDir=<seforim.db.lucene> -PluceneQueryCache=off               # build/parity/jvm.txt
./gradlew :search:iosSimulatorArm64Test -PindexDir=<seforim.db.lucene> -PluceneQueryCache=off # build/parity/ios.txt
```

They dump what the search answers on a real index (`SearchDump`). `-PluceneQueryCache=off` turns off Lucene's query
cache: it changes the last digits of the scores from one search to the next. Two runs differ anyway by Lucene's
process-dependent clause order (`BooleanQuery` rewrites through a `HashMap` keyed by class identity hashes), so the
comparison allows score differences: facets, snippets and highlights must be identical. On Android, Zayit's
`searchkit-check` app runs the whole search on a device or an emulator.

Verified on the real index (7M documents): the desktop, the iOS simulator and Android 11 emulator give the same facets,
snippets, highlights, titles and find-in-book candidates (Zayit's `searchkit`, hybrid with the semantic search: the
same dump as the desktop, but for a hit total Lucene counts as a lower bound).
